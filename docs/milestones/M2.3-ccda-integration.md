# M2.3 — C-CDA Integration

**Repository:** `healthcare-ai-data-platform`
**Milestone:** M2 — Healthcare Data Integration
**Submilestone:** M2.3
**Status:** Draft — Proposed for Approval
**Target branch:** `feat/m2-3-ccda-integration`
**Primary standard:** HL7 CDA Release 2 / C-CDA 5.0.0
**Runtime:** Python 3.12+, FastAPI, PostgreSQL, Silo (S3-compatible object storage)

---

## 1. Executive Summary

M2.3 introduces a C-CDA (Consolidated Clinical Document Architecture) ingestion capability into the Healthcare AI Data Platform.

The integration will accept C-CDA XML documents, securely validate and parse their document structure, extract selected clinical document metadata and section content, and persist the original document and its parsed representation.

The implementation extends the existing M2 ingestion foundation established by:

- M2.1 — FHIR R4 Integration.
- M2.2 — HL7 v2 MLLP Integration.

C-CDA is a document-oriented clinical exchange format. Unlike HL7 v2 messages, which are exchanged as individual messages, C-CDA represents clinical information in structured XML documents containing a document header, narrative sections, and potentially structured clinical entries.

The implementation must preserve the original document as the authoritative source. Parsed representations are derived data and must never replace or modify the original document.

### Primary objectives

1. Accept C-CDA XML documents through an authenticated ingestion API.
2. Identify supported C-CDA document types and versions.
3. Perform secure XML parsing and structural validation.
4. Extract document metadata, patient identifiers, author, custodian, encounter context, and clinical sections.
5. Preserve original XML documents in Silo.
6. Persist ingestion metadata and parsed representations in PostgreSQL.
7. Provide idempotency, auditability, retry handling, and reconciliation.
8. Integrate with the existing platform architecture without disrupting FHIR and HL7 v2 functionality.

## 2. Standards and Version Policy

### 2.1 Primary baseline

The initial implementation targets:

- HL7 Clinical Document Architecture (CDA), Release 2.
- Consolidated CDA (C-CDA), Release 5.0.0.
- US Realm Header constraints.
- Supported document templates defined by C-CDA 5.0.0.

C-CDA 5.0.0 is the primary implementation baseline for this milestone.

The implementation must use the official published implementation guide and its template definitions rather than relying on undocumented assumptions or hardcoded examples.

### 2.2 Legacy compatibility

C-CDA 2.1 documents are common in existing healthcare interoperability environments.

The implementation should recognize C-CDA 2.1 documents and provide controlled legacy ingestion where the document uses supported CDA R2 structures and supported document types.

Legacy documents must:

- Retain their detected version and source template identifiers.
- Be identified as legacy-profile documents.
- Not be reported as validated against C-CDA 5.0.0.
- Be rejected or marked unsupported when required structural information cannot be safely interpreted.

The implementation must not silently relabel a C-CDA 2.1 document as C-CDA 5.0.0.

Version detection and validation outcomes must be independently represented.

### 2.3 Important distinction

C-CDA 5.0.0 uses FHIR R5 StructureDefinitions and ElementDefinitions to define its templates.

However, the exchanged clinical documents remain CDA XML documents based on CDA Release 2.

This milestone does not implement FHIR R5 resource ingestion or C-CDA-to-FHIR transformation.

## 3. Initial Supported Document Types

To keep the implementation bounded, the first release supports three document types.

| Document type | Purpose | Priority |
|---|---|---|
| Continuity of Care Document (CCD) | Summary of relevant patient administrative, demographic, and clinical information | Required |
| Discharge Summary | Summary of a patient's hospital admission and discharge | Required |
| Progress Note | Clinical status during hospitalization, outpatient visits, or other encounters | Required |

All supported documents must conform to the applicable document template and header requirements of the detected C-CDA profile.

### Out of scope for the initial release

The following document types are not required for M2.3:

- Consultation Note
- History and Physical
- Operative Note
- Procedure Note
- Referral Note
- Transfer Summary
- Care Plan
- Unstructured Document
- Patient-generated document

The parser may recognize these document types, but it must not report them as fully supported when their profile-specific parsing and validation are not implemented.

Unsupported document types must produce an explicit, deterministic outcome.

## 5. C-CDA Ingestion Workflow

The ingestion process must follow a controlled sequence.

1. Receive an authenticated C-CDA XML request.
2. Enforce request size and content-type limits.
3. Generate a raw document SHA-256 hash.
4. Establish an ingestion identity and record the ingestion attempt in PostgreSQL.
5. Perform secure XML parsing.
6. Verify CDA document structure and namespace.
7. Detect the C-CDA version and document type.
8. Validate supported document templates and required header constraints.
9. Extract document metadata and supported clinical sections.
10. Store the original XML in Silo.
11. Persist parsed metadata and extracted representation in PostgreSQL.
12. Finalize ingestion status and audit information.
13. Return a deterministic API response.

### 5.1 Durable ingestion attempts

An ingestion attempt must be recorded before performing external Silo storage operations.

The system must preserve enough information to identify:

- The ingestion request.
- The source system, where provided.
- The document identifier.
- The original document hash.
- The processing status.
- The detected document type and profile version, when available.
- Failure category and retry eligibility.
- Processing timestamps and duration metrics.

A failed object-storage operation must not result in an ingestion attempt disappearing from the database.

### 5.2 Idempotency

The implementation must support idempotent ingestion.

Use a combination of:

- Source system identity, when supplied.
- CDA document identifier.
- Original XML SHA-256 hash.

Expected behavior:

| Scenario | Expected behavior |
|---|---|
| Same source, same document ID, same hash | Return existing ingestion result without duplicating stored data |
| Same source, same document ID, different hash | Treat as a document revision or conflict according to an explicitly implemented versioning policy |
| Different source, same document ID | Keep source identities isolated |
| Same content, different request | Avoid duplicate raw object storage where safe |

Concurrency must be handled using database-level constraints and appropriate locking.

An application-level check alone is insufficient.

The original document must never be overwritten by a later revision.

### 5.3 Original document storage

Store the original XML bytes in Silo.

Requirements:

- Preserve the exact received document bytes.
- Calculate and persist SHA-256.
- Use deterministic object keys based on the content hash.
- Preserve immutable document versions.
- Verify object-storage results before marking ingestion successful.
- Do not store raw clinical document content in application logs.

Suggested object key:

```text
ccda/{sha256-prefix}/{sha256}.xml
```

The exact key convention must be consistent with the existing Silo storage implementation.

## 6. Secure XML Parsing and Validation

XML security is a critical requirement.

C-CDA documents are untrusted external input and must be treated accordingly.

### 6.1 XML security requirements

The parser must:

- Disable DTD processing.
- Disable external entity resolution.
- Disable external network access.
- Prevent XML external entity (XXE) attacks.
- Prevent entity expansion attacks.
- Disable XInclude processing unless explicitly required and safely implemented.
- Enforce bounded document size.
- Enforce bounded parsing depth and resource consumption.
- Reject malformed XML.
- Handle unexpected namespaces safely.
- Avoid loading schemas or other resources from arbitrary external URLs.

The XML parser library and configuration must be documented.

The implementation must not rely on the XML document's own schema location to retrieve remote schemas.

### 6.2 Request limits

Use a configurable maximum request size.

Initial default:

```text
CCDA_MAX_DOCUMENT_SIZE_BYTES=10485760
```

This is a 10 MiB limit.

The implementation may introduce additional bounded parsing controls where supported by the chosen XML library.

Requests exceeding configured limits must be rejected before expensive parsing or storage operations.

### 6.3 Validation stages

Validation must distinguish between different failure categories.

| Validation stage | Requirement |
|---|---|
| XML well-formedness | Required |
| CDA namespace and root element | Required |
| Document identifier | Required |
| Document type identification | Required |
| C-CDA version detection | Required |
| Supported document template identification | Required |
| Required header constraints | Required |
| Profile-specific structural validation | Required for supported profiles |
| Full terminology validation | Out of scope unless explicitly implemented |

Validation must use pinned, local implementation artifacts where applicable.

Runtime retrieval of validation artifacts from arbitrary external services is prohibited.

### 6.4 Validation outcomes

The implementation must distinguish at least:

- `valid`
- `invalid_xml`
- `unsupported_document_type`
- `unsupported_profile_version`
- `invalid_document_structure`
- `missing_required_header`
- `validation_error`

The final internal status model may follow existing platform conventions, provided these outcomes remain distinguishable.

### 6.5 Validation is not clinical approval

A structurally valid C-CDA document does not imply that its clinical content is correct, complete, or safe for clinical decision-making.

The platform must not describe successful XML validation as clinical validation.

## 7. Metadata and Clinical Content Extraction

The parser must extract document metadata and selected clinical content without changing the source document.

### 7.1 Document header

Extract, where present:

- CDA document identifier.
- Document template identifiers.
- Document type code.
- Document title.
- Document effective time.
- Document language.
- Confidentiality code.
- Realm code.
- Record target / patient identifiers.
- Patient name, where permitted by the synthetic test environment.
- Author identifiers and timestamps.
- Custodian organization.
- Legal authenticator, where present.
- Encompassing encounter information, where present.

Missing optional fields must be represented explicitly as absent or null.

The parser must not invent values or infer clinical facts from missing fields.

### 7.2 Clinical sections

Extract section metadata:

- Section template identifiers.
- Section code and coding system.
- Section title.
- Section ordering.
- Section narrative content.
- Section-level structured entry references.

The initial parser must support the common section structures used by the three required document types.

At minimum, test fixtures must cover the following section families where applicable:

| Section | Example information |
|---|---|
| Problems | Patient problems and diagnoses |
| Allergies and Intolerances | Allergy information |
| Medications | Medication information |
| Results | Laboratory and diagnostic results |
| Vital Signs | Blood pressure, temperature, heart rate, and related observations |
| Encounters | Relevant encounter information |
| Procedures | Relevant procedures |
| Immunizations | Immunization information |
| Social History | Relevant social history |

The presence of a section is not guaranteed for every document type.

The parser must preserve section ordering and distinguish absent sections from present but empty sections.

### 7.3 Narrative and structured entries

C-CDA sections may contain both narrative text and structured clinical entries.

The implementation must:

- Preserve narrative content as supplied.
- Extract structured entry information where supported.
- Preserve the relationship between sections and their entries.
- Avoid assuming structured entries contain all clinical information.
- Avoid replacing narrative content with generated summaries.
- Avoid treating narrative and structured entries as interchangeable.

The original XML remains the authoritative representation.

### 7.4 Extraction limitations

M2.3 is a document ingestion and parsing milestone.

It is not a clinical terminology normalization project.

The implementation must not silently translate or reinterpret clinical codes.

Where a coding system is encountered, retain the original code, code system identifier, display name, and relevant original attributes when available.

## 8. PostgreSQL Data Model

The implementation should reuse the existing ingestion-attempt and audit patterns where practical.

New C-CDA-specific persistence structures may be introduced where necessary.

Expected logical entities:

### 8.1 C-CDA document record

Represents an ingested document.

Expected fields include:

- Internal document ID.
- Source system identity.
- CDA document identifier.
- Document type.
- Detected C-CDA profile version.
- Original document SHA-256.
- Silo object key.
- Document effective timestamp.
- Patient identifier reference.
- Ingestion status.
- Creation and update timestamps.

### 8.2 Parsed document representation

Stores extracted metadata and document structure.

Expected content:

- Header metadata.
- Patient identifiers.
- Author and custodian information.
- Encounter metadata.
- Section metadata.
- Extracted narrative content.
- Supported structured entries.
- Parser version.
- Validation outcome.
- Extraction timestamp.

JSONB is acceptable for hierarchical parsed representations.

The schema must not duplicate the complete original XML unnecessarily.

### 8.3 Ingestion attempts and audit

Record:

- Attempt identity.
- Document identity.
- Attempt status.
- Retry count.
- Processing start and completion timestamps.
- Processing duration.
- Failure category.
- Retry eligibility.
- Last error classification.
- Reconciliation information.

Do not store sensitive XML payloads or patient clinical content in error messages.

### 8.4 Migration requirements

The next database migration number should follow the existing migration sequence, currently ending at 011.

Expected migration:

```text
012_ccda_document_ingestion.sql
```

The exact filename may be adjusted if the implementation plan requires multiple migrations.

Requirements:

- Additive migrations only.
- No destructive changes to existing FHIR or HL7 v2 tables.
- No table recreation or data loss.
- Include matching fresh-initialization SQL.
- Ensure migration and initialization SQL remain consistent.
- Preserve existing data.
- Include indexes and constraints required for idempotency and reconciliation.

Migration execution must be tested against the existing local database.

Do not reset or destroy the local database to make tests pass.

## 9. API Requirements

Expose an authenticated C-CDA ingestion endpoint using existing API conventions.

Suggested endpoint:

```http
POST /api/v1/ingestion/ccda
```

The endpoint should accept:

- C-CDA XML document bytes.
- Optional source system identifier.
- Optional idempotency metadata, if supported by the shared ingestion API.

The API must enforce authentication and configured request limits.

### 9.1 Successful response

A successful response should provide:

- Internal ingestion/document ID.
- CDA document identifier.
- Detected document type.
- Detected profile version.
- Validation outcome.
- Ingestion status.
- Idempotency indicator.

### 9.2 Error handling

Use consistent HTTP status codes and structured error responses.

At minimum:

| Condition | Expected HTTP behavior |
|---|---|
| Missing or invalid authentication | 401 / 403 according to existing auth conventions |
| Oversized document | 413 |
| Unsupported media type | 415 |
| Malformed XML | 400 |
| Unsupported document type/profile | 422 |
| Duplicate document | Existing result or 409 according to identity policy |
| Storage/database dependency failure | 5xx |

The implementation must not expose raw XML, patient identifiers, stack traces, or internal storage credentials in API error responses.

### 9.3 Status and health

Reuse the existing health and readiness conventions.

If document-specific status endpoints are introduced, they must follow existing authentication requirements.

Public health and readiness endpoints must not expose clinical document data.

## 10. Retry, Recovery, and Reconciliation

The C-CDA ingestion workflow must support durable recovery.

Requirements:

- Persist ingestion attempts before Silo operations.
- Distinguish retryable infrastructure failures from permanent validation failures.
- Do not retry malformed XML or unsupported document profiles indefinitely.
- Use bounded retries.
- Use lease-based recovery where consistent with M2.2.
- Prevent concurrent workers from processing the same attempt.
- Fence stale workers from overwriting newer attempt outcomes.
- Preserve attempt history.
- Keep terminal outcomes terminal.
- Make reconciliation safe to run repeatedly.

The implementation should reuse M2.2 recovery patterns rather than introducing a separate retry framework.

A reconciler must be testable without requiring destructive database operations.

## 11. Security and Privacy

Security controls are mandatory.

### 11.1 Authentication and network exposure

- Reuse existing Bearer authentication.
- Keep protected ingestion routes authenticated.
- Bind published development service ports to loopback.
- Do not expose the local ingestion service publicly.
- Do not introduce cloud deployment as part of this milestone.

### 11.2 Sensitive data handling

- Use synthetic or legally authorized test documents only.
- Never commit real patient data.
- Do not log raw C-CDA XML.
- Do not log patient names, identifiers, or clinical narratives.
- Avoid exposing patient data in exception messages.
- Keep secrets in environment configuration, not source code.

### 11.3 Storage security

- Keep Silo credentials outside source control.
- Preserve original documents without modification.
- Restrict access through existing service credentials.
- Verify object-storage behavior and failure handling.
- Do not expose Silo management credentials through the API.

### 11.4 XML attack protection

All XML security requirements in Section 6 are acceptance requirements, not optional hardening.

The test suite must include malicious XML fixtures.

### 11.5 Compliance statements

This project is an engineering portfolio and interoperability demonstration.

It must not claim:

- HIPAA compliance.
- Clinical safety certification.
- Regulatory approval.
- Production clinical readiness.

Security controls are engineering safeguards, not proof of regulatory compliance.

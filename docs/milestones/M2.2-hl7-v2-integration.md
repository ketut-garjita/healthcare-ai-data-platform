# M2.2 — HL7 v2 Integration

**Repository:** `healthcare-ai-data-platform`  
**Milestone:** M2 — Healthcare Data Integration  
**Submilestone:** M2.2  
**Status:** Planned  
**Depends on:** M1 Foundation and M2.1 FHIR R4 Integration

---

## 1. Objective

Implement an HL7 v2 integration adapter that enables the Healthcare AI Data Platform to receive, parse, validate, persist, and audit healthcare messages using the HL7 Version 2 messaging standard.

The implementation must follow the existing modular ingestion architecture established in M2.1.

HL7 v2 messages and FHIR resources are different input formats, but they should share common ingestion principles:

- Raw data capture
- Input validation
- Idempotency
- Data quality checks
- Persistent storage
- Version and processing history
- Audit logging
- Error handling and recovery

The primary goal is to establish a reliable HL7 v2 ingestion capability, not to implement a complete healthcare interoperability engine.

## 2. Scope

### 2.1 Supported message categories

The initial implementation focuses on three HL7 v2 message categories.

| Category | Message type | Description |
|---|---|---|
| ADT | ADT^A01 | Patient admission |
| ADT | ADT^A02 | Patient transfer |
| ADT | ADT^A03 | Patient discharge |
| ADT | ADT^A04 | Patient registration |
| ADT | ADT^A08 | Patient information update |
| ADT | ADT^A40 | Patient identifier merge |
| ORM | ORM^O01 | General order message |
| ORU | ORU^R01 | Unsolicited observation result |

The implementation should use message-type-specific validation and parsing rules.

Unsupported message types must be rejected or recorded as unsupported without silently accepting them as successfully processed.

### 2.2 HL7 v2 version support

- Implement version-aware parsing.
- Use HL7 v2.5.1 as the initial reference version and test baseline.
- Keep version handling configurable and extensible.
- Reject unsupported or malformed message versions with an appropriate error response.
- Avoid assuming that all sending systems use the same HL7 version.

### 2.3 Message transport

Implement inbound HL7 v2 communication using MLLP (Minimal Lower Layer Protocol).

MLLP framing:

- Start block: `0x0B`
- End block: `0x1C`
- Carriage return: `0x0D`

Requirements:

- Receive complete messages using MLLP framing.
- Support multiple messages over a connection where appropriate.
- Handle incomplete frames and connection interruptions.
- Apply configurable message-size limits.
- Apply configurable connection and read timeouts.
- Keep the MLLP listener configurable and restricted to the local development environment by default.

The transport layer must remain independent from the HL7 parsing and ingestion services.

### 2.4 Acknowledgment handling

Implement HL7 acknowledgment handling.

Initial acknowledgment codes:

| Code | Meaning | Usage |
|---|---|---|
| AA | Application Accept | Message successfully accepted and durably persisted |
| AE | Application Error | Processing or validation error |
| AR | Application Reject | Unsupported or rejected message |

Requirements:

- Generate ACK messages with the appropriate MSH and MSA fields.
- Preserve the original message control ID in the acknowledgment.
- Do not return AA before the message has been durably captured and its ingestion state recorded.
- Return an appropriate error acknowledgment when persistence or processing fails.
- Handle duplicate messages idempotently.

ACK handling must be tested for success, duplicate delivery, malformed messages, and storage failures.

## 3. Architecture

The HL7 v2 adapter should integrate into the existing platform architecture.

### Logical ingestion flow

MLLP Receiver  
→ HL7 v2 Message Adapter  
→ Message Framing and Validation  
→ HL7 Parser  
→ Shared Ingestion Pipeline  
→ Raw Message Storage (Silo)  
→ Metadata and Parsed Representation (PostgreSQL)  
→ Processing Result and ACK

### Component responsibilities

**1. MLLP Receiver**

- Accept inbound HL7 v2 messages.
- Handle MLLP framing.
- Enforce connection and payload limits.
- Forward complete messages to the adapter.

**2. HL7 v2 Adapter**

- Identify message type and version.
- Extract MSH metadata.
- Invoke the appropriate message parser.
- Apply message-specific validation.
- Produce a structured representation.

**3. HL7 Parser**

- Parse segments, fields, repetitions, components, and subcomponents.
- Preserve segment ordering.
- Handle HL7 escape sequences.
- Support optional and repeated segments.
- Preserve unknown or Z segments rather than silently discarding them.

**4. Shared Ingestion Pipeline**

Reuse the ingestion principles established in M2.1:

- Durable ingestion attempt creation
- Raw payload storage
- Validation and normalization
- Idempotency
- Audit logging
- Retry and reconciliation
- Explicit processing outcomes

Avoid duplicating FHIR-specific business logic in the shared pipeline.

## 4. Data Storage

### 4.1 Raw message storage — Silo

Store the original received HL7 v2 message in Silo.

Requirements:

- Preserve the original payload bytes, including segment delimiters and encoding.
- Use content-addressed object keys based on SHA-256.
- Store the original payload independently of parsed or normalized representations.
- Record the object key and checksum in PostgreSQL.
- Do not overwrite an existing raw message.
- Do not automatically delete raw objects during failed ingestion or reconciliation.

Suggested object-key convention:

`hl7-v2/{sender}/{yyyy}/{mm}/{dd}/{sha256}.hl7`

Object keys must use sanitized identifiers and must not expose sensitive patient information.

### 4.2 Metadata and parsed representation — PostgreSQL

Introduce HL7-specific database structures.

Suggested logical entities:

**hl7_messages**

Stores the current message record and its metadata.

Potential fields:

- id
- message_control_id
- sending_application
- sending_facility
- receiving_application
- receiving_facility
- message_type
- trigger_event
- hl7_version
- message_timestamp
- raw_object_key
- raw_sha256
- parsed_message JSONB
- lifecycle_status
- created_at
- updated_at

**hl7_message_versions**

Stores historical versions or distinct payload revisions when appropriate.

**hl7_ingestion_attempts**

Stores individual processing attempts and their outcomes.

Potential fields:

- id
- message_id
- status
- outcome
- error_code
- sanitized_error_message
- started_at
- completed_at

These are logical design proposals. Inspect the existing M2.1 database conventions before finalizing table definitions.

### 4.3 Idempotency

Use message identity and sender context to identify duplicates.

At minimum, consider:

- Sending application
- Sending facility
- MSH-10 message control ID
- Raw payload SHA-256

Expected behavior:

| Scenario | Expected outcome |
|---|---|
| Same sender, control ID, and payload | Duplicate / unchanged |
| Same sender and control ID, different payload | Conflict requiring explicit handling |
| Different sender, same control ID | Independent message |
| Previously failed message retried | Retry without losing audit history |

Do not silently overwrite previously accepted messages.

## 5. Message Parsing and Initial Normalization

The initial implementation should extract useful structured information without attempting to build a complete clinical data model.

### ADT messages

Relevant segments:

- MSH — Message Header
- EVN — Event Type
- PID — Patient Identification
- PV1 — Patient Visit
- NK1 — Next of Kin / Associated Parties

Extract basic metadata such as:

- Patient identifiers
- Patient demographics when present
- Event type
- Encounter or visit identifiers
- Admission, transfer, and discharge information when present

### ORM messages

Relevant segments:

- MSH — Message Header
- PID — Patient Identification
- PV1 — Patient Visit
- ORC — Common Order
- OBR — Observation Request

Extract:

- Order identifiers
- Placer and filler order numbers
- Order status
- Order type
- Patient and encounter references
- Order timestamps

### ORU messages

Relevant segments:

- MSH — Message Header
- PID — Patient Identification
- PV1 — Patient Visit
- ORC — Common Order
- OBR — Observation Request
- OBX — Observation Result

Extract:

- Observation identifiers
- Observation values
- Units
- Reference ranges when supplied
- Result status
- Result timestamps
- Associated patient and encounter references

### Normalization principles

- Preserve the original message.
- Preserve parsed segment structures.
- Do not discard unsupported fields.
- Do not assume all optional fields are present.
- Do not infer missing clinical information.
- Do not perform clinical interpretation or diagnosis.
- Keep terminology and code-system mappings extensible.

FHIR transformation is not part of M2.2 acceptance. It can be addressed in a future interoperability milestone.

## 6. Reliability and Error Handling

The implementation must handle:

- Malformed MLLP frames
- Invalid HL7 messages
- Unsupported message types
- Unsupported HL7 versions
- Missing mandatory segments
- Invalid message control IDs
- Duplicate deliveries
- Conflicting message identities
- Silo unavailable
- PostgreSQL unavailable
- Interrupted connections
- Retry and reconciliation after partial failures

Important implementation requirements:

- Persist ingestion attempts before external object-storage operations where applicable.
- Keep network I/O outside PostgreSQL transactions holding resource locks.
- Use bounded retries.
- Make terminal ingestion states immutable.
- Do not lose audit history during retry.
- Ensure that a late failure handler cannot overwrite an already completed attempt.
- Make recovery behavior observable.

Follow the established M2.1 reliability patterns where applicable, without coupling HL7 processing to FHIR-specific database tables.

---

## 7. Security

- Use synthetic or legally authorized test data only.
- Never commit real patient information or PHI.
- Keep local listener ports bound to loopback by default.
- Enforce maximum message size.
- Apply connection timeouts and safe error handling.
- Avoid logging complete HL7 payloads.
- Avoid exposing patient identifiers in error messages or application logs.
- Sanitize sender identifiers used in storage keys.
- Keep credentials and secrets outside source control.
- Document the limitations of local security controls.

Do not claim HIPAA compliance or clinical safety certification.

## 8. Observability

Provide structured logs and processing metrics.

Suggested metrics:

- Total messages received
- Messages accepted
- Messages rejected
- Parsing failures
- Duplicate messages
- Conflicting messages
- Processing duration
- ACK response duration
- Silo storage failures
- PostgreSQL persistence failures
- Retry and reconciliation counts

Logs must avoid recording complete message contents or unnecessary patient identifiers.

## 10. Implementation Phases

### M2.2.1 — HL7 v2 Foundation

- Evaluate and select the HL7 v2 parsing library.
- Implement MLLP framing and receiver.
- Parse MSH metadata.
- Identify message type, trigger event, and version.
- Implement message-size and connection limits.
- Add unit tests using synthetic HL7 messages.

### M2.2.2 — ADT Integration

- Implement ADT message parsing.
- Support A01, A02, A03, A04, A08, and A40.
- Extract basic patient and encounter information.
- Add validation and structured representation.
- Add unit and integration tests.

### M2.2.3 — ORM and ORU Integration

- Implement ORM^O01 parsing.
- Implement ORU^R01 parsing.
- Extract order and observation information.
- Preserve segment relationships and repetitions.
- Add unit and integration tests.

### M2.2.4 — Persistence and Reliability

- Store original messages in Silo.
- Store metadata and parsed JSONB in PostgreSQL.
- Implement message idempotency.
- Implement version/history handling.
- Implement durable ingestion attempts and audit.
- Implement retry and reconciliation behavior.

### M2.2.5 — ACK and Unified Ingestion

- Implement AA, AE, and AR acknowledgments.
- Integrate with the shared ingestion pipeline.
- Verify ACK behavior for duplicates and failures.
- Add end-to-end integration tests.
- Update documentation and architecture diagrams.

- Existing ingestion attempts

## 12. Acceptance Criteria

M2.2 is complete when:

1. The platform can receive HL7 v2 messages using MLLP.
2. MSH metadata is correctly extracted.
3. The initial ADT, ORM, and ORU message types are supported.
4. Message parsing preserves segment ordering and repeated structures.
5. Unsupported and malformed messages are handled explicitly.
6. Original message bytes are stored in Silo.
7. Message metadata and parsed representation are persisted in PostgreSQL.
8. Idempotency and conflict handling work correctly.
9. Ingestion attempts and audit history are durable.
10. ACK responses follow the defined acceptance and error behavior.
11. Retry and reconciliation are tested.
12. Mandatory integration tests pass with zero skipped tests.
13. All existing M1 and M2.1 regression tests pass.
14. Documentation and architecture diagrams are updated.
15. Security limitations and production risks are documented.

---

## 13. Out of Scope

The following are explicitly excluded from M2.2:

- X12 270/271 and 837 integration.
- C-CDA ingestion.
- Outbound HL7 v2 message generation.
- Full bidirectional HL7/FHIR transformation.
- Complete enterprise interface-engine functionality.
- Clinical decision support.
- Clinical diagnosis or treatment recommendations.
- Production hospital connectivity.
- Multi-tenant production deployment.
- AWS deployment and infrastructure provisioning.

These capabilities can be considered in later milestones.

## 14. Engineering Constraints

- Keep implementation modular and incremental.
- Preserve M1 and M2.1 functionality.
- Reuse shared ingestion capabilities where appropriate.
- Avoid unnecessary abstraction and premature optimization.
- Use additive database migrations.
- Keep migrations consistent with fresh initialization SQL.
- Use synthetic or legally authorized data only.
- Do not modify `main` directly.
- Use a dedicated feature branch:

`feat/m2-2-hl7-v2-integration`

- Do not merge or push without explicit approval.
- Do not perform destructive database operations.
- Do not deploy to cloud infrastructure without explicit approval.
